# Документація тестів

Набір перевіряє API Teach UA (Speak Ukrainian) на dev-сервері
`http://speak-ukrainian.eastus2.cloudapp.azure.com/dev/`.
Джерело контракту — Swagger UI цього ж сервера (`swagger-ui/index.html`).

Є три види перевірок:

- публічні GET-ендпоінти міст і гуртків (без токена);
- CRUD гуртка під JWT і заборони CRUD міста для ролі менеджера;
- Swagger UI як сторінка: секції, діалог авторизації, виконання `GET /api/city/{id}` з браузера.

Окремо в репозиторії лишився стартовий приклад Playwright (`tests/example.spec.ts`). Він ходить на playwright.dev і не стосується API.

## Як запускається набір

Конфігурація — `playwright.config.ts`. Усі spec-файли лежать у `tests/`, але їх розведено по **проєктах**. Проєкт — це окремий запуск зі своїм `testDir`, `baseURL` і браузером.

| Проєкт | Що виконує | baseURL | Браузер |
| --- | --- | --- | --- |
| `swagger` | `tests/api/**` | dev-сервер | не потрібен: це HTTP-клієнт |
| `swagger-ui` | `tests/swagger-ui/**` | dev-сервер | Desktop Chrome |
| `chromium`, `firefox`, `webkit` | усе, крім `api/` і `swagger-ui/` | немає | відповідний браузер |

`testIgnore: ['**/api/**', '**/swagger-ui/**']` у браузерних проєктах відсікає API-спеки. Інакше `cities.get.spec.ts` і `club.crud.spec.ts` пішли б ще раз у Chromium, Firefox і WebKit без `baseURL`.

`fullyParallel: true` дозволяє тестам одного файлу йти паралельно. Тому тести не ділять токен, створений гурток чи інший стан: кожен викликає `signIn` сам і прибирає за собою.

На CI (`CI` у середовищі) увімкнені `forbidOnly`, два ретраї і один worker. Trace знімається лише на першому ретраї (`trace: 'on-first-retry'`). Репортер — HTML (`npx playwright show-report` або `npm run report`).

### Скрипти

```bash
npm test                  # усі проєкти
npm run test:swagger      # tests/api
npm run test:swagger-ui   # Swagger UI у headless Chrome
npm run test:headed       # той самий Swagger UI з видимим браузером
npm run report
```

`npm run test:api` викликає `--project=api`. Такого проєкту в конфігурації немає: API-тести зібрані в проєкті `swagger`.

Облікові дані для `signIn` читаються з `.env` у корені репозиторія:

```
USER_EMAIL=...
USER_PASSWORD=...
```

Файл підхоплює `process.loadEnvFile('.env')` на початку CRUD-спек. Це API Node, не пакет `dotenv` (його імпорт у конфігу закоментований). Змінні потрібні лише тестам, які логіняться. Публічні GET їх не читають.

## Механізми

### `request` і `page`

Playwright підставляє фікстури в аргумент тесту.

`request` — це `APIRequestContext`: HTTP-клієнт без браузера. Відносний шлях на кшталт `api/clubs` склеюється з `baseURL` проєкту `swagger`. Саме тому в спеках немає повного URL.

`page` — вкладка браузера. Її використовує лише `tests/swagger-ui/swagger-ui.spec.ts`. Проєкт `swagger-ui` додає `devices['Desktop Chrome']`, тож у цього запуску є viewport, user agent і рушій Chromium.

Обидві фікстури ізольовані на тест: свій контекст запитів або своя сторінка, і Playwright закриває їх після тесту.

### Перевірки

`expect(response.status()).toBe(200)` порівнює код відповіді. Далі тіло читається через `response.json()`.

Три способи порівняти JSON, і вони різні навмисно:

- `toEqual` — повний збіг об’єкта. Місто «Київ» маленьке і стабільне, тому список і картка порівнюються цілком.
- `toMatchObject` / `objectContaining` — збіг лише названих полів. Картка гуртка містить службові поля, які тест не фіксує.
- `arrayContaining` — елемент є в масиві, решта масиву може бути будь-якою. Так перевіряється, що серед гуртків є Jerome IT School, а не що список складається лише з нього.
- `expect.any(Number)` — id існує і має тип, точне значення задає сервер.

`content-type` перевіряється лише в публічних GET: відповідь має бути JSON. CRUD спирається на статус і тіло.

### Авторизація

Захищені ендпоінти описані в Swagger як bearer JWT.

1. `POST api/signin` з `email` і `password` з `.env`.
2. Очікується `200` і тіло `{ accessToken }`.
3. Далі кожен запит несе заголовок `Authorization: Bearer <token>`.

Токен не кешується між тестами і не пишеться у `storageState`. Паралельний запуск не може зіпсувати чужу сесію, бо сесії немає: є лише рядок у локальній змінній тесту.

### Ізоляція і прибирання гуртка

`club.crud.spec.ts` створює дані. Щоб паралельні тести і повторні прогони не чіпляли один одного:

- ім’я містить мітку сценарію і `Date.now()` (`Test Club post 1729...`);
- тест сам створює гурток і в `finally` викликає `DELETE /api/club/{id}`;
- спільних `beforeAll` / фікстур із даними немає.

`finally` спрацьовує і коли перевірка тіла впала: гурток не лишається на dev-сервері. Виняток — тест `DELETE`: він сам видаляє гурток і перевіряє `200`, тому другого delete немає.

Допоміжні `createClub` і `removeClub` — це не окремі тести. Вони готують і прибирають дані для GET і PUT. Сам сценарій створення перевіряє окремий тест `POST /api/club`, бо там дивляться і на тіло відповіді `201`.

### Опис гуртка — це не рядок

Поле `description` сервер зберігає як JSON редактора Draft.js: `blocks`, `entityMap`, стилі. Порівнювати весь JSON крихко: сервер може переписати `key` або порожні масиви стилів.

`draftDescription` збирає такий документ з одного блоку тексту. `expectDescription` парсить обидва рядки і порівнює лише `blocks[].text`. Перевіряється зміст опису, а не байт-у-байт серіалізація.

Категорія гуртка — існуюче ім’я з довідника: `Програмування, робототехніка, STEM`. У відповіді `GET /api/club/{id}` вона приходить уже об’єктом `{ id, name }` у масиві `categories`, тому тест шукає її через `objectContaining({ name })`, а не порівнює масив цілком.

### Чому місто не створюється

Користувач з `.env` має роль, якій Swagger дозволяє читати місто. `POST`, `PUT` і `DELETE /api/city` для неї відповідають `403`. Тести це фіксують і не намагаються створити місто.

`GET /api/city/1` читає вже наявний запис «Київ» (`id: 1`, координати `50.4501`, `30.5234`). PUT і DELETE б’ють у той самий id, але очікують `403`, тож запис не змінюється. Тіло PUT навмисно повторює поточні назву і координати: навіть якби авторизація зламалась і сервер прийняв запит, дані Києва лишились би тими самими.

Публічні `GET /api/cities` і `GET /api/city/1` у `cities.get.spec.ts` повторюють читання без токена. Це інший контракт: ендпоінт відкритий, відповідь — JSON, Київ є в списку і збігається повністю.

### Swagger UI

`swagger-ui.spec.ts` не кличе API напряму. Він відкриває сторінку документації і натискає її елементи.

`beforeEach` на кожен тест:

1. відчиняє `swagger-ui/index.html` (знову відносний шлях від `baseURL`);
2. чекає заголовок `Teach UA API` до 30 секунд — специфікація підвантажується після HTML;
3. у випадаючому списку серверів обирає dev server.

У `describe` стоїть `timeout: 60_000`, бо сторінка важча за один HTTP-виклик, а стандартні 30 секунд на весь тест замало.

Локатори прив’язані до розмітки Swagger UI, не до власних `data-testid`:

- `.info .title` — назва API;
- `#operations-tag-city` і `#operations-tag-club` — секції City API і Club API;
- кнопка `Authorize` відкриває `.dialog-ux` зі схемою `bearer`; тест лише перевіряє, що діалог є, і закриває його — токен у Swagger UI не вводить;
- блок операції знаходиться як `.opblock`, усередині якого є кнопка `get /api/city/{id}`.

Сценарій Execute:

1. розгорнути операцію;
2. `Try it out`;
3. вписати `1` у єдине текстове поле (id);
4. **до кліку** підписатися на `page.waitForResponse` для URL, що закінчується на `/api/city/1`;
5. натиснути `Execute`;
6. дочекатися цієї відповіді і перевірити статус `200`;
7. у таблиці live response прочитати код `200` і текст `Київ`.

`waitForResponse` ставиться раніше за клік, інакше відповідь може прийти до того, як тест почне її чекати, і очікування зависне до таймауту.

## Каталог тестів

### `tests/api/cities.get.spec.ts`

Публічне читання міст. Без логіну.

| Тест | Дія | Очікування |
| --- | --- | --- |
| `GET /api/cities` | список | `200`, JSON, список не порожній, у ньому є Київ |
| `GET /api/city/{id}` | `GET api/city/1` | `200`, JSON, тіло точно дорівнює Києву |

### `tests/api/clubs.get.spec.ts`

Публічне читання гуртків. Орієнтир — гурток `id: 1`, Jerome IT School, вік 2–18, категорія id `4`.

| Тест | Дія | Очікування |
| --- | --- | --- |
| `GET /api/clubs` | список | `200`, JSON, список не порожній, у ньому є цей гурток |
| `GET /api/club/{id}` | картка id `1` | ті самі поля плюс категорія в `categories` |

Ці тести залежать від даних dev-сервера. Якщо гурток 1 перейменують або приберуть, спека впаде. На відміну від CRUD, тут нічого не створюється.

### `tests/api/club.crud.spec.ts`

Повний цикл під токеном. Кожен тест: `signIn` → свої дані → `finally` з `DELETE`, крім тесту видалення.

| Тест | Дія | Очікування |
| --- | --- | --- |
| `POST /api/club` | створити гурток | `201`, є числовий `id`, name / вік / текст опису збігаються |
| `GET /api/club/{id}` | прочитати щойно створений | `200`, ті самі поля, категорія в `categories` |
| `PUT /api/club/{id}` | прочитати поточний стан, змінити name, опис, вік 7–12, `isOnline: true` | `200`, у відповіді нові значення |
| `DELETE /api/club/{id}` | видалити щойно створений | `200` |

PUT спочатку робить GET і розкладає відповідь через `...current`. Так у запит потрапляють поля, які сервер вимагає, але тест їх не змінює. Поверх копії записуються лише name, description, ageFrom, ageTo, isOnline.

Вхідна схема створення: `name`, `description`, `ageFrom`, `ageTo`, `categoriesName` (масив рядків), `isOnline`.

### `tests/api/city.crud.spec.ts`

Та сама роль, інший ресурс. Місто не створюється.

| Тест | Дія | Очікування |
| --- | --- | --- |
| `POST /api/city` | спроба створити `Test City post <timestamp>` | `403` |
| `GET /api/city/{id}` | прочитати Київ | `200`, тіло дорівнює `{ id: 1, name: 'Київ', ... }` |
| `PUT /api/city/{id}` | спроба записати ті самі дані Києва | `403` |
| `DELETE /api/city/{id}` | спроба видалити Київ | `403` |

### `tests/swagger-ui/swagger-ui.spec.ts`

| Тест | Дія | Очікування |
| --- | --- | --- |
| `shows city and club sections` | відкрити документацію | на сторінці є City API і Club API |
| `authorizes with the bearer dialog` | Authorize → Close | діалог зі схемою `bearer` з’являється і зникає |

### `tests/example.spec.ts`

Два тести-шаблони Playwright: заголовок playwright.dev містить `Playwright`, посилання Get started веде на сторінку з заголовком Installation. Їх виконують проєкти `chromium`, `firefox` і `webkit`. До Teach UA вони не підключені.

## Що навмисно не покрито

- Немає окремого тесту на прострочений або порожній токен.
- DELETE гуртка перевіряє лише `200` відповіді видалення, без повторного GET «вже немає».
- Swagger UI не проганяє POST/PUT/DELETE і не вводить пароль у діалог Authorize.
- Негативні кейси валідації (поганий вік, порожнє ім’я, невідома категорія) не написані.
